# Unity test scene

Status: **implemented, works with the real controller on macOS.** Still
to check by hand: that the critter's motion has the right signs and feels
right (see [Done when](#done-when)).

## Goal

A very small, slightly fun Unity scene that proves the controller works inside
Unity, before any real game code:

- A little **critter** (a round body with eyes, feet, tail and an antenna)
  **mirrors the controller's yaw, pitch and roll** in real time.
- **Button A** (touch A on the Waveshare board = HID button 1) **cycles its
  colour**; **button B** (HID button 2) makes it **hop**.
- An on-screen **debug readout**: device name, report rate, the raw report in
  hex, buttons, hat, angles, and every input device Unity sees.

It is a developer test bench, so it is visual on purpose. The real game is
audio-only (see [vision.md](vision.md)). Haptics are out of scope for this
first scene (see [roadmap.md](roadmap.md#2-haptics-from-unity)).

## Running it

1. Power the controller. It reconnects to an already-paired Mac by itself
   (first time: pair it in System Settings → Bluetooth, see the [README](../README.md#1b-pair-on-macos)).
2. Open `unity/EchoQuestTest` with Unity **6000.6.8f1** (Unity Hub, or `unity open unity/EchoQuestTest`).
3. Open `Assets/EchoQuest/Scenes/ControllerTest.unity` and press **Play**.
4. Hold the controller flat, screen up, top edge pointing at the screen.

| Input | Effect |
|---|---|
| Turn / tilt / roll the controller | The critter turns / tilts / rolls the same way |
| A (HID button 1) | Next colour |
| B (HID button 2) | Hop |
| Hold A + B for 1 s, or press R | Recenter yaw (the critter faces the yellow marker) |
| No controller: arrows, Q/E, 1, 2 | Keyboard fallback for yaw/pitch, roll, A, B |

Yaw starts at 0 when the controller powers on and drifts slowly (no
magnetometer), so recenter whenever the critter's heading is off.

## Project layout

```
unity/EchoQuestTest/                      Unity 6000.6.8f1, URP, Input System 1.20.1
  Assets/EchoQuest/
    Scripts/EchoQuestController.cs        Input System device for our HID report (mirrors protocol/hid-report.md)
    Scripts/CritterController.cs          orientation -> rotation, A = colour, B = hop, recenter, keyboard fallback
    Scripts/ControllerDebugHud.cs         IMGUI debug overlay
    Scripts/EchoQuest.asmdef              runtime assembly (unsafe code on, for reading raw state events)
    Editor/TestSceneBuilder.cs            builds the scene from code (menu: EchoQuest > Rebuild Controller Test Scene)
    Scenes/ControllerTest.unity           generated by TestSceneBuilder; don't hand-edit, change the builder
    Materials/*.mat                       generated by TestSceneBuilder
  Packages/manifest.json                  includes com.unity.pipeline (lets the Unity CLI drive the Editor)
```

The scene is **generated from code**: to change it, edit `TestSceneBuilder.cs`
and rebuild (menu item, or `unity command eval --code
'EchoQuest.Editor.TestSceneBuilder.Build();'`). That keeps it reproducible and
easy for an AI agent to change without editing scene YAML.

## How Unity sees the controller (findings, 2026-11-04, macOS)

- **macOS:** the Editor could read the controller without asking for extra
  permission (Input Monitoring was not needed on this machine).
- **Device description:** interface `HID`, product `EchoQuest-555A` (the
  advertised name), manufacturer `EchoQuest Team`, capabilities
  `vendorId 4617 (0x1209)`, `productId 1`, `usagePage 1`, `usage 5`,
  `inputReportSize 16`, `outputReportSize 9`, `featureReportSize 1`.
- **State = the raw input report, report ID first:** 16 bytes, byte 0 = `0x01`.
  Offsets are exactly the protocol doc's "host offsets". Checked by decoding
  the raw bytes by hand against the displayed angles.
- **Unity's generic HID fallback is not suitable.** Without a custom layout,
  the Input System builds one from the descriptor (named
  `HID::EchoQuest Team EchoQuest-XXXX`) that turns X/Y (yaw/pitch) into a
  `stick` with a radial deadzone and an **inverted Y**, and adds `axisDeadzone`
  processors to the other axes. That distorts angles. So the project registers
  its own layout, **`EchoQuestController`**, matched on interface `HID` + VID +
  PID, which reads every field as documented: `button1`..`button16`, `hat`
  (0–8) plus a `dpad`, and `yaw`/`pitch`/`roll`/`axis3..5` as SHRT axes
  normalised to −1..1 (× 180 = degrees).
- **The product name includes the MAC suffix**, so match on VID/PID, not on name.
  When the firmware's PID is bumped (descriptor change), update
  `EchoQuestController.ProductId` and the layout together.
- **Output report size is 9** (report ID + 8 bytes), as documented, so sending
  haptics from Unity looks feasible. Not tried yet.
- **Read controls from `Update`, not `OnGUI`.** In the Editor, reading device
  controls from `OnGUI` returned a different, stale state buffer. The HUD
  builds its text in `LateUpdate`.
- **Report rate:** hidapi receives about 95–100 reports/s while the controller
  moves, as the firmware intends. Unity's `InputSystem.onEvent` counter shows
  about 16% more state events than that. Values are correct; the extra events
  are probably duplicates the Input System generates itself. Not investigated.

## Repository setup

The repo-root `.gitignore` was generated for several stacks and broke Unity
projects. Fixed on 2026-11-04:

- Removed `*.meta` (Visual Studio section): Unity `.meta` files must be committed.
- Removed `**/[Pp]ackages/*` (NuGet section): Unity's `Packages/manifest.json`
  and `packages-lock.json` must be committed.
- The root file's Unity rules are anchored to the repo root, so the project
  has its own `unity/EchoQuestTest/.gitignore` (Library, Temp, Logs,
  UserSettings, generated `.csproj`/`.slnx`, ...).

Check before committing Unity changes: `git status --untracked-files=all unity`
must list no `Library/`, `Temp/`, `Logs/` or `UserSettings/` paths, and every
asset should come with its `.meta`.

## How it was built (AI-assisted)

Built by Claude Code driving the Unity Editor through the **Unity CLI**
(details in [development-workflow.md](development-workflow.md#unity)):

1. `unity projects create "EchoQuestTest" --path unity --editor-version 6000.6.8f1 --template com.unity.template.urp-blank`
2. `unity pipeline install --project-path unity/EchoQuestTest` (before the first open).
3. `unity open unity/EchoQuestTest`, then `unity status --until-ready`.
4. Device discovery with `unity command eval` (list `InputSystem.devices`, read the controller's description and raw state).
5. Scripts written as files; scene generated with `TestSceneBuilder.Build()` through `unity command eval`.
6. Verified with `unity command editor.playmode start`, frame-counter checks (Play mode really advancing), `unity command capture game_view` screenshots, and `unity command console get`.
